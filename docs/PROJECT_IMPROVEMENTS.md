# Предложения по улучшению проекта

Документ собран после просмотра основных модулей проекта: `README.md`, `requirements.txt`, `web_gui.py`, `transcription.py`, `llm_cloud_eval.py`, `sheets_export.py`, `audio_io_safe.py`, `operator_staff.py`, `benchmark_calls.py`.

## Короткий вывод

Проект уже решает реальную прикладную задачу и выглядит как рабочий MVP с сильной доменной настройкой под ЕКЦ. Главный потенциал роста сейчас не в добавлении ещё одной функции, а в повышении предсказуемости: упростить архитектуру, централизовать конфиг, закрыть базовую безопасность, добавить автоматические проверки и сделать пакетную обработку более надёжной.

## Приоритет 1. Надёжность и безопасность

### 1. Убрать небезопасные значения по умолчанию

- В `web_gui.py` сейчас есть дефолтный пароль админ-панели `9632`.
- В `sheets_export.py` и `.env.example` зашит production-like `DEFAULT_SPREADSHEET_ID`.

Что улучшить:

- Требовать `ADMIN_PANEL_PASSWORD` из окружения и не поднимать админ-панель без него.
- Перенести ID таблицы из кода в конфиг, а при отсутствии явно показывать статус "не настроено".
- Для чувствительных ключей рассмотреть `streamlit.secrets` или системное хранилище.

Эффект: меньше риска случайного доступа к настройкам и записи не в ту таблицу.

### 2. Вынести конфигурацию в единый слой

Сейчас проект читает `os.environ` во многих местах: UI, Google Sheets, облачный LLM, пост-редактор, аудио-пайплайн.

Что улучшить:

- Сделать единый `config.py` с `dataclass` или `pydantic-settings`.
- Загружать и валидировать конфиг один раз на старте.
- Для каждого блока иметь явные секции: `asr`, `cloud_eval`, `google_sheets`, `security`, `batch`.

Эффект: меньше скрытых зависимостей, проще отладка, легче поддерживать `.env.example`.

### 3. Добавить автоматические проверки качества

В репозитории не видно `tests/`, `pytest`, `ruff`, `mypy`, `pyproject.toml`, `pre-commit` и CI.

Что улучшить:

- Добавить `pytest` хотя бы на критические функции: разбор имён файлов, вычисление пропуска ожидания, сборку строк для Google Sheets, нормализацию имён операторов.
- Подключить `ruff` и базовый `pre-commit`.
- Добавить GitHub Actions с шагами `python -m compileall`, `pytest`, `ruff check`.

Эффект: проще вносить изменения в большой код без страха сломать рабочие сценарии.

### 4. Явно зафиксировать прямые зависимости

В `requirements.txt` нет `scipy`, хотя проект импортирует `scipy.signal` в `audio_io_safe.py` и `scipy.optimize` в `speaker_voice_dual_encoder.py`.

Что улучшить:

- Добавить прямые зависимости, которые используются напрямую.
- По возможности перейти на `pyproject.toml` и lock-файл.
- Разделить extras: `base`, `ui`, `cloud`, `dev`.

Эффект: меньше сюрпризов при установке на новом окружении.

## Приоритет 2. Архитектура и поддерживаемость

### 5. Разделить монолиты `web_gui.py` и `transcription.py`

Сейчас самые крупные файлы проекта:

- `web_gui.py` около 2500 строк
- `transcription.py` около 3200 строк
- `llm_cloud_eval.py` около 1100 строк

Что улучшить:

- Вынести из `web_gui.py` отдельные модули: `ui/sidebar.py`, `ui/single_file.py`, `ui/batch.py`, `ui/renderers.py`.
- Вынести из `transcription.py` сервисы: `asr`, `audio_preprocess`, `diarization`, `role_assignment`, `reporting`, `qa`.
- Оставить в точках входа только orchestration-код.

Эффект: быстрее разбираться в коде, проще покрывать тестами и безопаснее менять отдельные части пайплайна.

### 6. Ввести явные request/result-модели между слоями

Сейчас `run_analysis()` и `Transcriber(...)` передают много параметров напрямую, а UI знает слишком много о внутреннем устройстве пайплайна.

Что улучшить:

- Сделать `AnalysisRequest`, `AnalysisOptions`, `AnalysisArtifacts`, `ExportRow`.
- Передавать в сервисы не десятки аргументов, а 1-2 объекта.
- Убрать мутирование `transcriber.skip_first_seconds` и `_log` извне.

Эффект: меньше неявного состояния, понятнее интерфейсы между модулями.

### 7. Перевести прогресс и логи на структурированные события

Сейчас UI обновляет прогресс через разбор текстовых логов и промежуточное состояние.

Что улучшить:

- Вместо строк логов ввести события вида `stage_started`, `stage_progress`, `stage_finished`, `warning`, `artifact_saved`.
- Хранить код этапа и полезную нагрузку отдельно от человекочитаемого текста.
- Логи оставить для оператора, а прогресс строить по структуре.

Эффект: меньше хрупких зависимостей между текстом логов и интерфейсом.

### 8. Вынести доменные правила из кода в конфиг или данные

Сейчас важные бизнес-правила зашиты в код:

- список операторов и алиасы в `operator_staff.py`
- leniency-логика для отдельных операторов там же
- большие prompt-блоки в `llm_cloud_eval.py`
- текстовые стандарты в отдельном корневом файле

Что улучшить:

- Хранить такие правила в `yaml/json` с версией схемы.
- Добавить валидацию структуры и changelog для доменных правил.
- Для чувствительных правил оценки держать явный audit trail: кто и когда их менял.

Эффект: бизнес-изменения можно будет вносить без тяжёлого редактирования Python-кода.

## Приоритет 3. UX и эксплуатация

### 9. Усилить механизм пакетной обработки

Сейчас состояние batch-режима хранится в `результаты/.batch_resume_state.json`, а авто-возобновление завязано на `time.sleep(1)` и `st.rerun()`.

Что улучшить:

- Вынести batch-state в отдельный каталог состояния приложения, а не в папку пользовательских результатов.
- Добавить версию формата checkpoint.
- В перспективе перевести пакетную обработку в отдельный worker/service-слой, чтобы UI только наблюдал за задачей.

Эффект: меньше хрупкости при падении UI, проще продолжать обработку и отлаживать сбои.

### 10. Выравнять поведение CLI и Streamlit

Сейчас Streamlit-путь и CLI-путь частично расходятся: логика экспорта, настройка моделей и состав передаваемых данных отличаются.

Что улучшить:

- Сделать единый application-service для анализа звонка.
- CLI и UI должны вызывать один и тот же слой.
- Экспорт в Google Sheets и сборка отчёта должны работать через общие функции без "урезанных" веток.

Эффект: меньше расхождений между режимами запуска и легче сопровождать новые возможности.

### 11. Расширить наблюдаемость и benchmark-контур

`benchmark_calls.py` уже есть, это хорошая база для регрессий.

Что улучшить:

- Завести небольшой набор эталонных звонков или синтетических fixtures.
- Сохранять baseline-метрики по времени, роли, заполненности отчёта, cloud-fallback rate.
- Отдельно отслеживать частоту ручного review и причины fallback.

Эффект: улучшения качества можно будет доказывать числами, а не только ощущениями.

## Практический план на ближайшие шаги

Если делать улучшения поэтапно, я бы шёл так:

1. Добавить `pyproject.toml`, `pytest`, `ruff`, CI и прямые зависимости.
2. Ввести единый `AppConfig` и убрать пароль/таблицу по умолчанию из кода.
3. Вынести `run_analysis()` и batch-логику в сервисный слой.
4. После этого распилить `web_gui.py` и `transcription.py` на модули.
5. Последним этапом вынести доменные правила и prompt-данные в отдельные конфиги.

## Самые выгодные быстрые улучшения

- `pyproject.toml` + `ruff` + `pytest`
- `config.py` с валидацией окружения
- отказ от дефолтного пароля и дефолтной таблицы
- выделение batch-движка в отдельный модуль
- единый service-слой для CLI и Streamlit
